# 失敗カタログ

このベンチを作る過程で起きた失敗を、起きた順に全部残す。
`LEARNINGS.md` はエージェントに読ませる「やり方」だが、こちらは**計測系を作る側の記録**で、
エージェントには渡さない。研究資料の中核。

分類は2つ。

- **G（Goodhart）**: 指標は満点、成果物は劣化。エージェントが指標の穴を正しく突いた
- **H（Harness）**: 計測系の欠陥。エージェントの失敗に見えたが、原因は出題側

---

## G-1 絶対配置で座標をなぞる

**症状**: 1ターンで収束、layoutDiff 1.14%。一見すると大成功
**実際**: `absolute left-[222.5px] top-[124px]` で座標指定。絶対配置72%、flex/grid 半減、Radix 使用ゼロ
**なぜ**: ピクセル差分に最短で到達する方法が座標トレース
**検出**: `absolute / (absolute + flex + grid)` の比率。上限40%
**残る穴**: 小数px の固定 margin（`ml-[222.5px]`）は絶対配置比率に出ない

## G-2 画像領域を単色で潰す

**症状**: layoutMad 改善、judge 91点（前回90点より高評価）
**実際**: ヒーロー画像を `<div className="bg-[#d7d6b3]" />` の無地矩形に。中の「頭に汗 かいてる?」が消失
**なぜ**: 知見「画像は平均色の単色ブロックで置く」が、画像**領域**全体に過剰適用された
**検出**: judge にソースを読ませ `dropped`（落とした中身）を返させる
**教訓**: 判断基準は「画像かどうか」ではなく「**文字や図形として描けるか**」

## G-3 連番コピペ

**症状**: 17個のコンポーネントに分解済み。一見きれいな設計
**実際**: `Thumb1`〜`Thumb5` が props を取らない一品物。コピペをコンポーネントの形にしただけ
**検出**: 末尾が数字の部品名を検出

## G-4 挙動を持つ部品を素の div で組む

**症状**: 4試行連続で Radix の使用が `Avatar` 1個のみ
**なぜ**: 参照が静止画1枚。ドロップダウンを Radix で組んでも**閉じた状態のスクショは1pxも変わらない**
**検出**: 参照の要素と primitive の対応表を作り、充足率をゲートにする
**注意**: 対応表は人手。ここに設計判断が漏れている（未解決）

## G-5 画面を並べて「ページ」に見せる

**症状**: 断片6枚すべてが完璧に一致、順序も単調増加
**実際**: `h-[956px] overflow-y-auto` の容器を6個並べ、JSで各々を別位置にスクロール。
実際にスクロールするとヘッダーが6回現れ、要素が途中で切断される
**なぜ**: 「フルページ撮影に各断片が順番どおり現れること」を厳密に満たす最小構成
**検出**: 描画結果のDOMを見る（内部スクロール容器数・header数・高さがビューポート高の整数倍か）
**発見者**: 人間。指標もjudgeも通していた

## H-1 ぼかし半径が小さすぎ

**症状**: 3ターンかけてもスコアが動かない（-0.008pt）
**原因**: 2940px幅の参照に半径3。フォント差でテキスト全画素が不一致として残り、レイアウト改善が埋もれた
**修正**: 半径を画像幅に比例（幅/100）
**影響**: 「改善は1ターン目で全部」という誤った結論を出した

## H-2 指標の飽和

**症状**: layoutDiff が厳密に 0.000000
**原因**: pixelmatch は閾値超えの画素を数えるので、良くなると0で止まる
**修正**: 閾値を持たない連続量 `layoutMad`（ぼかし後の平均絶対差）を併用

## H-3 サンドボックス未リセット

**症状**: 2回目以降が速い
**原因**: 試行開始時に App.tsx を初期化していなかった
**修正**: プレースホルダから毎回リセット。ライブラリは意図的に残す

## H-4 サブエージェントの背景実行

**症状**: 内部ターン1・出力400トークン・スコア凍結が14ターン続く
**原因**: Agent SDK はサブエージェントを**既定でバックグラウンド実行**する。
ブレインが返った時点で builder はまだ書いており、1ターン前の状態を撮っていた
**修正**: `background: false` + 撮影前にファイルの静止を待つ

## H-5 撮影条件が参照と違う（sticky）

**症状**: 断片02〜06 が 5.3% の床で10ターン・$14 空転
**原因**: 参照はスクロールして撮られ sticky ヘッダーが全断片に写る。
フルページ撮影では sticky は先頭に1回しか描画されない。上端100pxが永久に不一致
**修正**: 位置はフルページで探し、**採点は参照と同じくスクロールして撮り直す**
**影響**: 存在しない壁でエージェントを10ターン走らせた

## H-6 judge に参照を1枚しか渡していない

**症状**: ページ全体が合格
**原因**: 断片モードを作ったとき `reference.webp`（断片01）だけを渡していた。6分の5が未審査
**発見**: judge 自身が申告した（「残り5枚を渡して再審査してください」）

## H-7 知見に答えが混入

**症状**: 1ターン収束が続く
**原因**: 知見に「このUIのCTAは #176bf5」等の実測値52行と、16進54個が混入。
測っていたのは「保存した答えを貼れるか」
**修正**: `cold`（固有値を `#______` に伏せる）/ `hot`（含む）/ `none` の3モードに分離

## H-8 フロー検査が状態変化前を測る

**症状**: ページ高が 2193px から動かない
**原因**: `inspectFlow` が `enterActions`（「続きを読む」クリック）を適用していなかった。
実際は 5467px あった

## H-9 位置探索が sticky 帯を除外しない

**症状**: 断片5枚すべてが位置0に張り付き、順序判定が永久に不合格
**原因**: H-5 の片側だけ直していた。採点は撮り直しで直したが、**位置探索はフルページ画像のまま**。
上端にヘッダーを持つ断片はページ先頭で最もよく一致する
**修正**: 全断片の上端で一致する範囲＝sticky帯を自動検出して照合から除外（実測196px＝CSS98px）
**影響**: 修正だけで収束 0/4 → 6/6 に変わった

## H-10 dev server が途中で落ちる

**症状**: 20試行中2件が `ERR_CONNECTION_REFUSED` で失敗
**原因**: builder が Bash で作業する過程で dev server が巻き込まれて落ちる
**修正**: 毎ターンの撮影前に生存確認し、落ちていたら立て直す

## H-11 結果をターゲットごとに分けていない

**症状**: 47試行を1つの表に並べ、平均ターン数を出していた
**実際**: 規模も難易度も違う4ターゲットが混在。ページ見出しは先頭1件のターゲット名
**修正**: ターゲット別に集計。条件（知見モード・変種）を `summary.json` に記録
**影響**: 「A/Bに差なし」を一度報告したが、条件を記録していなかったため事後検証できなかった


## H-12 連番検出の誤検出

**症状**: `⚠連番 SectionH2` が出続ける
**実際**: `SectionH2` は `<h2>` を出す単一部品。`SectionH1` / `SectionH3` は存在しない。
末尾が数字というだけで「Thumb1 / Thumb2 型のコピペ」と判定していた
**修正**: 同じ語幹の部品が**2つ以上**あるときだけ連番とみなす
**教訓**: ゲートに昇格させる前に、検出器の誤検出率を実物で確認する。
警告のうちは害が無いが、ゲートにすると正当な実装を落とす


## H-13 ブレインの query() が無音で固まる

**症状**: ターン1の出力が25分出ない。App.tsx はリセット直後のまま、ライブラリも空
**実際**: tsx 配下のプロセスは CPU 0.0%、Claude のサブプロセスが存在せず、会話ログも生成されていない。
エラーにもならず、ただ待ち続けていた
**なぜ気づきにくいか**: H-10（dev server 落ち）は例外が出て FAILURE.txt に残るが、これは**何も起きない**。
grep で絞ったログには「反復 1/2」の1行しか出ず、外からは「遅いだけ」と区別がつかない
**修正**: ターンごとに AbortController でタイムアウト（既定20分、`UI_BENCH_TURN_TIMEOUT_MS`）。
中断したら subtype=timeout として FAILURE.txt に残し、試行を終える
**教訓**: 「エラーが出ない失敗」は監視の穴になる。進捗が無い状態に上限を置く
**追記1**: タイムアウトを入れて計測したところ4試行中2件で再発したように見えた。
健全な query は数秒で最初のメッセージを返すので、最初の応答を120秒で見切って1回やり直す形にし、
SDK の debugFile も run に残すようにした
**追記2（訂正）**: その後の3件を調べると、**全部スリープの偽陽性**だった → H-14。
「50%がハング」は誤り。CPU 0%・サブプロセス無しで固まった最初の1件だけが未解明のまま

## H-14 壁時計のタイムアウトがノートPCのスリープを数える

**症状**: 20分タイムアウトが3試行連続で発火。FAILURE.txt は「応答なし」
**実際**: `pmset -g log` で、その時間帯はバッテリー53%で Maintenance Sleep を15分周期で繰り返していた。
SDK デバッグログの末尾は「first byte after 948ms」— **API は正常に応答していた**。
setTimeout は寝ている間も進むので、起きた瞬間に「20分経過」として発火した
**なぜ気づきにくいか**: FAILURE.txt の文面が H-13 と同じ「応答なし」。ログだけ見ると同じ失敗に見える
**修正**: 5秒ティックの無応答監視に変更。ティックが30秒以上飛んでいたら停止とみなし、
その分を無応答時間から除外する。試行のバッチは `caffeinate -i` で包み、アイドルスリープを止める
**教訓**: 長時間バッチの前に「PC を閉じるか」を聞く。閉じるなら電源に繋ぐ。
タイムアウトの判定には「なぜ止まったか」を区別する材料（pmset・SDKログ）を必ず残す

## H-15 記事ページ用の文面のまま、ダッシュボードにフロー検査をかけた

**症状**: grafana-play 反復3。ターン1で `header 4 · ⚠ 1本の流れになっていない`。
ターン2は builder が Bash を約50回・10分動いたのに **App.tsx が1行も変わらず**、指標も lib のハッシュも同一。
ターン3でようやく通過。無駄にした: 1ターン・約15分・$1
**実際**: フロー検査は「画面の複製」を `document.querySelectorAll('header').length` で見ていた。
Grafana のパネル見出し帯を `<header>` にするのは正当な HTML で、複製ではない。
さらに brain へのフィードバック文面が **「参照は1本の記事ページ」「断片ごとにセクションを複製しない」** と
newspicks 専用の言葉のままだった。ダッシュボードには当てはまらないので、builder は探し回って直すものを見つけられなかった
**なぜ気づきにくいか**: ゲート名が「フロー」で汎用に見える。文面はターゲットを増やしたときに読み返していない
**修正**: ページ幅（ビューポートの6割以上）か sticky/fixed の header だけを数える。文面をターゲット非依存に。
brain の最終発言を `turn-NN.brain.md` に残す（SDK のデバッグログには本文が残らず、この調査で原因を直接読めなかった）
**追記（再発）**: 幅6割で切る修正のあと、antd-pro-form-advanced で再発（カードの見出し帯が幅 77%）。
ターン1を落として $5 を無駄にした。「幅」は複製の証拠ではない。
**同じ文面のヘッダーが繰り返す**か、sticky/fixed が複数あるかだけを見る形に変更
**教訓**: ゲートを1ターゲットで作ると、判定も文面もそのターゲットの形を吸っている。
新しい種類のターゲットを足したら、**ゲートの文面を全部読み返す**。
「何も変わらなかったターン」は builder の怠慢ではなく、直せない指示を受けた印

## H-16 審査員が「84点」と「アバターがイニシャル」で落とし、予算を使い切らせた

**症状**: grafana-play（9/23）。ターン2で全ゲート通過、judge の点数は 90/87/84/89/87。
pass=false の理由は typography 84（基準85）と、「アバターが灰色の CA フォールバックのまま」
「サムネイル内の表の行間」「折り返しが2行でなく3行」。累計 $11.3 で予算 $12 に達し、そこで終了
**実際**: 目視では参照と同じ画面。落とした理由は再現不能な写真の代替と、20px 未満の幅のずれ。
pass の条件を「全項目85以上」という主観点数の閾値にしていたので、1点差で試行が丸ごと未収束になった
**なぜ気づきにくいか**: judge の issues は毎回もっともらしい。点数が閾値を跨いだだけだと気づくには
不合格の全件を並べて見る必要があった（並べたら不合格は直近1件だけで、それがこれだった）
**修正**: 指摘を blocking / minor に分けさせ、pass は **blocking・dropped・seamIssues が空か**でハーネス側が決める。
写真・サムネイル・アバターは枠の位置と大きさだけを見る、と明記。
予算は「1ターンの実測 × 2 以上」に（grafana 12→30、antd 12→24）
**教訓**: 主観点数に閾値を切ると、閾値の近くで結果がノイズになる。
収束判定は「直さないと駄目なものが残っているか」の二値で書かせる。
予算はターゲットの重さを見てから決める。最初の1ターンで 9 割使う設定は「打ち切り」と同じ

## H-17 1ビューポートぴったりの画面を「スクロールしない」で落とした

**症状**: antd-pro-settings 反復2。ターン1で `header 1` なのに「1本の流れになっていない」。
理由は「ドキュメント自身がスクロールしません」。高さ 956px = ビューポート高
**実際**: 参照自体が1画面に収まる設定画面。反復1は高さ 958px（2px はみ出し）で通り、
反復2は 956px で落ちた。**2px の差で合否が変わる**判定だった
**修正**: 「スクロールしない」は内部スクロール容器があるとき（中身が閉じ込められている）だけ問題にする
**教訓**: フロー検査の各条件は「複製された画面」を捕まえるための代理指標。
代理指標を単独で合否に使うと、それが成り立たない正当な画面で誤検知する。
H-15・H-17 は同じ根。**新しい種類の画面を足すたびに代理指標を全部疑う**

## H-18 期待 primitive の重なりで、ターンごとに1つずつ落とす

**症状**: antd-pro-settings 2回とも。ターン1で `Form` 未使用 → ターン2で Form を入れたら
`Label` を Form.Label に置き換えて `Label` が未使用 → ターン3でようやく全部。反復2は $16
**実際**: 抽出エージェントが `Form` と `Label` を両方挙げる。Radix の Form.Label は Label と同じ役割なので、
builder が Form に寄せると Label が消える。ゲートは名前で見ているので「落とした」と判定した
**修正**: `Form` を使っていれば `Label` は満たしたとみなす（Form.Label は Label）。
知見に「期待リストは書き始める前に全部確認し、1ターン目で全部入れる」を追加
**教訓**: 期待リストは抽出エージェントの出力で、重なりや粒度のぶれがある。
名前の一致で採点するなら、**同じ役割の primitive を同一視する表**が要る

## H-19 ネットワーク断を「エージェントが何も書かなかった」と数えた

**症状**: バッテリー駆動で蓋を閉じたまま回した none 条件の2試行。ターン1の brain の発言が
`API Error: Can't reach the API server (ENOTFOUND)`。App.tsx は placeholder のまま。
ハーネスはこれを普通のターンとして採点し、「3ターン変化なし」で **未収束** として記録した
**実際**: スリープ復帰直後は Wi-Fi 再接続まで API に届かない。SDK はそれでも `subtype: success` で返し、
本文にエラー文を入れる。H-14 のスリープ対策（無応答時間の除外）は効いていたが、
**復帰後に届かない**ケースは別の穴だった
**修正**: 本文が API Error ならターンを `network` として扱い、ネットワーク復帰を最大30分待って
同じ指示をやり直す。ターン開始前にも到達確認。復帰しなければ FAILURE.txt（ハーネス失敗）
**教訓**: 「成功」の型で返ってくる失敗がある。結果の本文も見る。
壊れた試行は統計に入れる前に FAILURE.txt を付けて分母から外す（今回は手で付けた）

## H-20 エージェントが過去の試行の成果物に届いていた

**症状**: antd-pro-analysis cold 反復3 の brain の発言:
「同一シェルで layoutDiff 0 だった **前回 antd-pro-settings のアイコンライブラリとヘッダー／サイドバーを描き直さず流用**させた」。
run に残った `lib/icons.tsx` は settings 反復の run のものと **バイト単位で同一**
**実際**: query の cwd がリポジトリ直下で、Glob / Grep / Bash の再帰探索が `runs/*/lib`、`runs/*/App.final.tsx`、
`targets/*/extracted.json`（抽出結果＝答案）、`harness/knowledge/`（マスク前の知見）、`.snapshots/` に届く。
「ライブラリ空・知見なし」という条件は、ファイルを消しても **探索で拾えるなら成立していない**
**規模**: 収束済み run の非自明行（40字以上）が過去の同ターゲット run にそのまま存在する割合は 0〜7%（1件 15%）。
丸ごとの写しは無かったが、部品単位の流用が起きていた。汚染が自己申告された1件は FAILURE 扱いで分母から外した
**修正**: PreToolUse フックで隔離（`harness/isolation.ts`）。runs/（自分の撮影先を除く）・知見原本・
スナップショット・抽出結果・他ターゲットへのアクセスを拒否し、Glob / Grep / 再帰 Bash は許可ディレクトリの明示を要求。
拒否は `isolation-denied.log` に残す。summary の conditions に `isolated: true` を記録
**追記（隔離後の実測）**: フックを入れた最初の5試行で拒否 23件。内訳は
`extracted.json`（答案）を cat しようとした 3件、`harness/knowledge/targets/<slug>.md` を探した 1件、
前回の run ディレクトリを ls した 3件、他は再帰探索。**none 条件のエージェントは答案を探しに行く**。
隔離前の試行は、読んでいなかった証拠がないので条件比較から外し（`隔離=なし` として別集計）、cold を取り直す
**教訓**: 「条件を揃えた」の証明は、消したことではなく **届かないこと**。
エージェントは cwd 配下を自由に探索する前提で、見せてよいものを列挙する側に回る。
brain の発言を保存していなければ（H-15 の修正）この流用は見つからなかった

## H-21 selftest が試行本体を読み込んでいなかった

**症状**: 6試行のバッチが全部、出力ゼロで即終了。直前の `pnpm selftest` は通っていた。
ログを見ると `ERR_PACKAGE_PATH_NOT_EXPORTED: './package.json' is not defined by "exports"`
**実際**: SDK の版を summary に残すため `require('@anthropic-ai/claude-agent-sdk/package.json')` を
run.ts のモジュール先頭に置いた。このパッケージは package.json を exports していないので、
**run.ts を import した瞬間に落ちる**。`tsc --noEmit` は型だけ見るので通り、
selftest は計測部品（capture/flow/structure/components）しか import していなかったので通った
**なぜ気づきにくいか**: 「試行前に selftest を通す」を手順にしていたのに、
その selftest が**試行本体を一度も読み込んでいなかった**。緑のチェックが嘘をついた
**修正**: SDK の版は `node_modules/.../package.json` を直接読む（失敗しても 'unknown'）。

## H-22 隔離の拒否を builder が「止まれ」と受け取って手を止めた

**症状**: grafana-play cold（隔離あり）が3ターン連続で何も変わらず未収束。App.tsx は placeholder の31行のまま。

**止まった理由は、cat でファイルを確認するコマンドが拒否されたこと**です。builder はそれを止まれという指示と受け取っていました」
**実際**: 拒否されたのは `cat targets/grafana-play/target.json; ls harness/knowledge/targets/` のような**複合コマンド**。
正当な部分と禁止パスが 1 コマンドに混ざっていた。拒否の文面は理由しか書いておらず、
「試行は続いている」「別のコマンドで続けてよい」が無かったので、builder は作業自体の中止と解釈した
**規模**: 1試行まるごと（$3.6、3ターン）。ほかの試行でも拒否は出ているが、そちらは自力で続けていた
**修正**: (1) 拒否の文面に「**この1コマンドだけを拒否した。試行は続いている。中止しないこと**」と
「; や && でつないだ場合は触れている部分だけ外して実行し直す」を明記。
(2) brain と builder のプロンプトに**見てよい場所の一覧を最初から書く**（拒否が出る前に避けられる）
**教訓**: 制約を後出しの拒否だけで伝えると、エージェントは最悪の解釈をする。
**禁止は事前に、拒否は「次にどうするか」つきで**返す。ガードレールは回復方法とセットで初めて機能する

## H-23 禁止事項を引用しただけで拒否した（隔離フックの自爆）

**症状**: antd-pro-analysis cold が3ターン無変化で未収束。App.tsx は placeholder のまま。

禁止事項を伝えたこと自体が、禁止事項に引っかかる構図
**規模**: 1試行（$4.7、3ターン）。H-22 と合わせて grafana と antd を1本ずつ潰した

**教訓**: 文字列一致のガードは、**ガードの説明文が入力に混ざる**ことを想定していない。

## H-24 モデルのエイリアスが実験の途中で別モデルに解決された

**症状**: アプリ画面の試行費用が $9〜17 から $1.2〜1.8 に落ちた。直前にガードレールを直していたので、

それは偶然で、確かめるまで分からなかった。モデルをまたいだ費用の比較は無効

「直したら良くなった」と思ったら、まず自分の修正以外に動いたものを探す

## H-25 失敗は記録していたが、知見は4日間更新していなかった

**症状**: 指摘されて数えたところ、`FAILURES.md`（ハーネスの欠陥）は当日まで 29 件に育っていたのに、
`LEARNINGS.md`（エージェントに渡す知見）は **4日前が最終更新**。`knowledge/history/` は10日前で停止。
`pnpm reflect`（振り返りエージェント）はその間**一度も動かしていなかった**
**実際**: その4日で約30試行を回し、judge の指摘も全部残っていたのに、そこから何も取り出していない。
cold 条件が測っていたのは「4日前の知見」で、知見が育つ前提そのものが止まっていた
**なぜ起きたか**: 振り返りが**手順書の中の約束**だったから。H-19〜H-24 の対処に追われると真っ先に落ちる
**修正**: 仕組みにした。
(1) `harness/knowledge/reflected.json` に振り返り済みの試行を記録
(2) `pnpm reflect --pending` で未反映をまとめて処理
(3) **未反映が12件を超えると selftest が落ちる** → バッチを始める前に必ず気づく

## H-26 フックが中断され、許可済みのパスまで拒否された

**症状**: 記事ターゲットの知見あり 1本が3ターン無変化で未収束。App.tsx は placeholder のまま。
brain の発言:「許可されているパス（`packages/ui/src/index.ts`、`slice-02.webp`）の読み取りまで
『The user doesn't want to take this action right now. STOP』で拒否されました。
これは禁止パスの自動拒否ではなく、あなたからの停止指示だと判断しました」
**実際**: 隔離フックの拒否ログは**空**。SDK のログにこう出ていた。

```
PreToolUse SDK callback hook cancelled (control stream closed); draining sibling hooks
[ERROR] hook failed: core: errorKind=AbortError (classic.PreToolUse; skipped)
[ERROR] hooks chain failed: errorKind=AbortError
```

フック自体が中断され、SDK はそれを拒否として扱う。
許可・禁止の判断以前の話なので、フックのロジックをいくら直しても防げない
**頻度**: 8試行中1件
**なぜ厄介か**: 拒否の文面が H-22（隔離フックの正当な拒否）と**同じ**。

`hooks chain failed: errorKind=AbortError` があれば**ハーネス失敗**として

**追記（頻度が上がった）**: 次のバッチでは 6試行中2件（33%）で再発。検出（FAILURE.txt 行き）だけでは
試行が3分の1失われる。**ターン単位で検出して同じ指示をやり直す**（最大2回）ようにし、
フックの `timeout` も 60 秒に伸ばした

フックを入れるなら「フックが死んだときの見分け方」と「死んだときの戻し方」を一緒に用意する

## H-27 状態ごとにページを読み直し、満たせない出題を作りかけた

**症状**: 状態つきターゲット（既定 / フォーム展開 / モーダル / 行選択）の参照を撮ったところ、
同じ行の値が状態ごとに違った（TradeCode 99 が 2830000 / 5200000 / 1730000）
**実際**: 状態ごとに `capture()` を呼んでいたので、そのたびにページを読み直していた。
参照側の表は乱数で作られるため、**全状態を同時に満たす実装が存在しない出題**になっていた。
廃止した `newspicks-article-full`（参照6枚が状態変化を跨いでいた）と同じ罠を、
仕組みを作り直した側で踏みかけた
**気づいた理由**: 撮った4枚を並べて見たから。数字が違うのは目で見れば一目で分かる
**修正**: 1回の読み込みの中で状態を移す。撮り終えたら `undo` の操作で既定状態に戻す
（モーダルなら Cancel、選択なら Clear）。読み直さないのでデータが変わらない
**教訓**: 出題が満たせるかどうかは、**参照を並べて見れば分かる**。
新しいターゲットを作ったら、走らせる前に全参照を目で確認する。
同じ罠を別の入口から踏みかけた = 一度直した欠陥は、仕組みを作り直すたびに再入場する

## H-28 関門を増やすばかりで、効いているかを一度も数えていなかった

**症状**: 「5段のゲートで機械的に判定している」と資料に書いていたが、
各関門が実際に何回落としたかを数えたことがなかった
**実際**（137ターンを集計）:
- フロー 23回（16.8%）・部品 22回（16.1%）・ピクセル(layoutDiff) 22回（16.1%）・審査 11回（8.0%）
- **ピクセル(rawDiff) は 97.8% が閾値内**。閾値30%はフォント字形差の床（9%前後）よりはるかに甘く、一度も止めていない
- **構造（絶対配置のトレース）は発火0回**。プロンプトで先に防いでいるので、関門としては働いていない
**なぜ問題か**: 止めていない検査を並べておくと「5段で守っている」と読み手も自分も誤解する。
実際に効いているのは4つで、そのうち1つ（審査）はスコアが 0.8 点ぶれる
**修正（当初）**: rawDiff を合否から外して記録専用にした
**修正の訂正**: 外すのは誤り。**発火0回の構造ゲートを保険として残しながら、
3回発火した rawDiff を外す**のは筋が通らない、と指摘されて考え直した。
判断の根拠は発火実績ではなく**守備範囲**だった。
layoutDiff はグレースケール化してぼかすので**色相の誤りを捨てる**。
レイアウトが合っていて色だけ違う実装は layoutDiff を通り、拾えるのは rawDiff だけ。
戻したうえで、閾値を 30% → **15%** に締めた
（他の関門を通った180ターンの rawDiff は最大 12.7%、15% 超えは0件なので誤検知は増えない）。
構造は保険として残し、発火0回であることを資料に明記する。
`pnpm audit:gates` で関門の効きをいつでも数え直せるようにした
**教訓**: 関門は足すときに「何を捕まえるか」を考えるが、
**捕まえ続けているかを後から数えない**。検査の数は安心の量ではない。
ただし**発火実績が少ないことは外す理由にならない**。
外していいのは「他の関門と守備範囲が重なっている」と示せたときだけで、
それは発火回数ではなく**指標が何を捨てているか**で決まる

## H-29 環境変数を忘れると、黙って別の条件で走る

**症状**: 切り分けのため手で1本流したところ、`conditions.variant` が **B** で記録された。

**比較できなくなる側を既定にしない**。バッチ台本では明示していたので気づかなかった

## H-30 レート制限を「ネットワーク断」と同じ扱いにして、試行を捨てた

**症状**: 5本のバッチが4本失敗。FAILURE.txt はすべて「ネットワークが復帰しませんでした（network）」。
7時間にわたるバッチで、1本は9ターン目まで進んでいた
**実際**: SDK のログを見ると2種類が混ざっていた。
**ENOTFOUND 22回**（本物の DNS 断）と **429 が14回**（サブスクの利用上限）。
私の監視は両方を「断」として同じに扱い、30分待って諦めていた。
上限は時間で必ず戻るので、捨てるのが最も損（1本 $2〜37）
**修正**: 429 / rate limit を `rate-limit` として区別し、20分待ってやり直す。
DNS 断の待ち時間も 30分 → **2時間**に延ばした（実測でそれを超える断があった）
**教訓**: 「つながらない」には**戻らないもの**と**待てば戻るもの**がある。
同じ扱いにすると、待てば済むものを捨てる。
長時間バッチでは、失敗の分類の粗さがそのまま損失になる
