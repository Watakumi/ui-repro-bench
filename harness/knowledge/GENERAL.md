# 再現の汎用知見

別のターゲット（まだ見たことのないサイトの画面）でもそのまま使える手順・失敗の型・判断の基準。
LEARNINGS.md（試行ごとに `pnpm reflect` が更新する知見）から、固有名詞と実測値を外して抜き出したもの。
特定の画面の実測値・座標・色・そのサイト特有の構造は `harness/knowledge/targets/<slug>.md` にある。

書き方のルール（このファイルを更新するとき）:
- **観察**（何が起きたか）と**対策**を対にする。対策だけ書くと、なぜそうするのかが失われて守られなくなる
- サービス名・サイト名・実測値は書かない。値が要る話はターゲット固有ファイルへ
- 項目は30を上限にする。溢れたら統合するか、効果の薄いものを落とす

座標の前提: 参照画像が @2x なら、測った元画素を2で割ると CSS px になる（下の「Read で見た画像は縮小されている」）。

## 測定（推測しない）

### 色は記憶から書かない。ブランド色・UIキットの既定色も「知っている色」に含む
**観察**: 「知っている青を書かない」と書いてあっても、SNS の公式ブランド色、UIキットの既定の文字色・主色、バッジサービスの既定色は「例外」として記憶から書かれた。
どれも参照の実測とずれていた。UIキットの主色は版によって違い、既定の副次テキスト色（不透明度 0.45 など）も参照とは段が違うことがある。
**対策**: 16進を1つ書くたびに `pnpm probe color <参照> <x> <y>` を叩き、出た値をそのまま貼る。主色の定数を書く前に主ボタンの面を1か所測る。
アイコンの中は白抜き文字があるので、**白に当たらない縁寄りの座標**を測る。

- **文字の色は平均で測らない**: `probe color` の平均は文字の細さで薄まる。白地なら横 scan の**最暗明度**を取り、`不透明度 ≒ 1 − 明度/255` で書く。暗い地では**最明度**で比べる
- **同じ画面でも部品の種類ごとに既定色が違う**: 同じ 14px でもサイドメニューとフォームラベルで不透明度が違う、埋め込みのテキストパネルとアプリ本体の UI で本文色・リンク色が違う、ということが実際にあった。全体の TEXT 定数を別の種類の部品に使い回さない。定数は**部品の種類ごとに1か所ずつ**測ってから決める
- **半透明の色は、白地と色地の2か所で測ると見分けられる**: 白地で1回測って一致しても、選択行・hover 行・ストライプの上で外れることがある（不透明で書くと色地で点が消える）。地の色が変わる状態がある部品は、白地と色地の同じ部品を両方測る。色地で値が動いたら半透明なので `rgba(0,0,0,α)` で書く（α = 1 − 白地の明度/255）
- **1部品に色が複数あるなら、色の数だけ測る**: 1色測ると残りも測った気になる。バッジなら左半分・右半分を1点ずつ、種類ごとに測る
- **描き込みの多い run でも、色は前回最良に負けることがある**: 色の定数は前回最良と `probe color` で突き合わせる
- **小さなアイコンボタン（「…」・展開ボタン）は地と記号の明暗を両方測る**: 参照は濃い地に白い記号なのに、UIキットの既定（薄灰の地に濃い記号）で書いて明暗が逆になった回が4回あった（run 12-19-34・12-32-47・15-52-00・15-58-08。後ろ2回は同じ薄い半透明の地 `#818b981f` で、参照の濃い地と明度差 140 以上）。幅も既定値の推測で、参照の 1.5 倍（12-32-47）の回も 0.6 倍（15-58-08）の回もあった。地の中央と記号の上を1点ずつ `--r 0` で測り、明度の大小が参照と同じ向きか確かめる。6回目（run 16-17-54）もまた `#818b981f` の薄い地だった（実装の地の明度 221、参照 99）。知見がない試行では、ほぼ毎回ここを外す。5回目（run 16-04-08）は明暗の向きが合い、地の明度も参照と差 8 だったが、幅は推測値で参照の 1.5 倍だった。judge はこれを「濃すぎる、淡くせよ」と書いたが、参照の地のほうが暗かった。明暗は測った向きで決め、judge の「淡く」で地を明るくしない。幅は地の横 scan で測る。7回目（run 16-25-24）も `bg-[#818b9833]` の薄い地に `h-3 w-4` の推測で、地の中央が `#dee2e6`（参照 `#59636e`）。judge は「小さく淡い」とだけ書いた。8回目（run 16-36-12）も `bg-[#818b981f] h-5 w-6` で地の中央 `#e8eaed`（参照 `#59636e`）。知見なしの8回中7回が薄い地で外した

```sh
pnpm probe color <参照> <x> <y>        # 半径4の平均。アンチエイリアスに強い
```

### 文字サイズは「行の右端がどこまで届くか」で判断しない。ink 高さと字送りで測る
**観察**: judge に「参照より小さい、拡大せよ」と言われた見出しが、実測では ink 高さで実装のほうが大きかった。
負の字間で行幅だけが短くなっていて、judge はそれを見て誤診した。指摘どおり拡大していたら悪化していた。
その回は、逆算すると実装はほぼ全ての文字（メタ行・見出し・数値・ナビ）が参照より大きかった。
**対策**: 参照と実装の同じ行を `probe crop --scale 4` で切り出し、**漢字の上端〜下端（ink 高さ）**と**字送り（同じ文字の左端から次の文字の左端まで）**で比べる。
実装の font-size は自分で書いた値が分かっているので、
`参照の font-size ≒ 実装の font-size × (参照の ink 高さ / 実装の ink 高さ)` で逆算できる（幅で比べるなら ink 幅の比）。

- **コードに書いた `text-[Npx]` の種類ごとに1か所ずつ測る**: 見出しと主役の数値だけ測って、副次の数値・ラベル・フッター・セクション見出しを測らない、が繰り返された。見出しで合っても副次は別の値のことが多い
- **UIキットの既定の font-size を書く癖は、知見がないと毎回同じ値で出る**: 同じターゲットで3回、同じ値の誤りが出た。ターゲット固有ファイルに値があればその値で書く
- **小さな記号（三角・矢印）は、幅と高さを縦横それぞれ scan で測って viewBox に入れる**。既定の縦横比で置かない
- **幅が合っても weight は外れることがある**: 同じ外接矩形の中の暗画素数（明度 110 未満）を参照と数える。幅で size、暗画素数で weight を決める
- **見出しは「区分ごとに1つ」測る**: 和文は字送り ≒ font-size なので、一行の ink 幅を字数で割った字送り（CSS 換算）を font-size の目安にする

### 和文に letter-spacing を入れない。ロゴはセリフ体にせず、ink で合わせる
**観察**: 見出しに負の tracking を入れると、文字自体は参照より大きいのに行は短い、という判別しづらい状態になった。
0.5px 大きくして字間で詰め直す書き方は、折り返しを1字ずらした。正の字間を足しても同じく折り返しがずれた。
折り返しのずれは tracking だけでなく、**右の padding** の差でも起きた。
ロゴでは、負の tracking で2語の隙間が消えた。逆に、下線を一部だけ引くために span を分けて gap を入れ、参照にない隙間を作った。
知見なしの回は、細いサンセリフのロゴを**毎回セリフ体＋下線**で書き、ロゴ1個の誤りでナビ全体が右へずれた（judge は5件のどれにも挙げなかった）。
さらに SVG の `textLength` で字の幅を指定しても、glyph の左右の余白が含まれるので ink は指定より細くなった。
**対策**: 和文の見出し・本文に tracking を入れない（0 のまま）。ロゴにも負の tracking を入れない。
参照のロゴがサンセリフならセリフ体を当てず sans のまま、上線・下線は border で描く。語の間は gap で空ける。
ロゴの寸法は textLength / width ではなく **ink で合わせる**: ロゴを通る横 scan で各字の左右端を参照と比べ、合うまで x と幅を動かす。
組んだら `probe pair <参照> <実装> <ロゴの矩形> --scale 3` で並べて見て、ロゴとナビ先頭の左端は自分で scan する。
行幅が合わないときは font-size を疑う。tracking で帳尻を合わせると ink 高さと行幅が食い違う。
**例外は画像の中の文字だけ**: ink 高さが参照と一致していて字送りだけ広い場合は、font-size を上げずに正の tracking で字送りを合わせる。ページ本文・見出しには適用しない。

### 1ターンで閾値を切っても、前回最良と同じ場所を `probe scan` で比べる。前より悪くなった部品は戻す
**観察**: 1ターンで閾値を切った run が、前回最良より数か所悪くなっていた。どれも閾値の 1/10 しか差分がなく、2ターン目を回す理由にならなかった。
一方で、1ターン・出力が半分でも、前回最良の部品を持ってきたうえで描き足していて**改善**だった run も多い。速さだけでは判定できない。
手抜きの型は決まっている: 前回最良が参照と一致させていた gap・幅・weight・font-size を、UIキットの既定値の推測で書き直す。描いていたアバター・図形を単色の円に戻す。
前回最良を読めない条件（isolated）では、推測で書き直した小部品が毎回同じ値で後退した。
**手抜きかどうかの見分け方**: absolute 比率・dropped・構造の指標に加え、出力トークンが前回最良の 1/3 以下になっていないかを見る。なっていれば、前回最良の部品を置き換えていないかソースの diff で確かめる。
**出力トークンは summary の値でなく metrics の `modelUsage.<モデル>.outputTokens` で比べる**: summary の `output_tokens` はサブエージェントの出力を含まない。5.3k と報告された回の実際の出力は 36.7k で、前回最良（62.6k、サブエージェントなし）の 1/12 ではなく 6 割だった（run 12-32-47）。ソースの行数（946 対 875）も同程度で、量を減らしたのではない。後退の原因は量ではなく、知見なしで既定値を推測したこと（identicon 0 個・バッジの色がバッジサービスの既定・アイコンボタンの明暗が逆）。知見なしの5回（12-09-04・12-32-47・15-41-44・15-52-00・15-58-08）で、後退した部品がほぼ同じだった（単色の円のアバター・タブの gap・アイコンボタンの明暗・表の列幅・バッジサービスの既定色）。15-58-08 は出力 5.6k・absolute 1%・dropped なしで、judge 86〜93 でも前回最良より悪い。1ターンで閾値を切っても、既定値の推測で速くなっただけで上達ではない。6回目の 16-04-08（2ターン、absolute 5%、dropped なし、judge 93〜95）も同じ部品が後退した（identicon 0・「緑の点」誤読・バッジサービスの既定色・重なった円を DOM 順）。アイコンボタンの明暗だけは初めて合った。judge の点が高いことは改善の根拠にならない。7回目の 16-25-24（出力 7.3k・1ターン・absolute 3%・judge 93〜95）も同じ部品（単色の円・円の個数・バッジサービスの既定色・アイコンボタンの明暗・回目の 16-36-12（出力 6.5k・1ターン・absolute 6%・dropped なし・judge 92〜95）も同じ（identicon 0・最新コミット行は単色の円1つ・バッジは Verdana 11px とバッジサービスの既定色・アイコンボタンの明暗が逆・タブの gap 推測）。
出力が少ないだけでは手抜きと決めない。出力が前回最良の 1/9（6.9k 対 62.6k）でも、absolute 3%・identicon あり・前回の誤読（重なったアバター）と色2つを直した改善だった run がある（run 11-50-21）。同じ条件の run 12-19-34（出力 6.4k・absolute 6%・identicon と重なったアバターあり）も、全体は前回最良と同等だった。ただし数値の小部品（タブの間隔・小ボタンの色）は推測で後退していた。判定は部品単位の diff と probe で行う。
summary が 7.2k でも modelUsage は 77.8k（前回最良 62.6k 超）・absolute 3%・dropped なしで、色は固有値どおりに直っていた回（run 12-39-35）も手抜きではない。ただし前回最良から持ってこずに書き直した小部品（重なりの前後・「+」の文字サイズ・バッジの padding）だけは後退していた。後退は「持ってこなかった部品」に集中する。
知見が汎用だけの isolated の回（run 12-57-50: modelUsage 62.8k で前回最良と同量・absolute 1%・dropped なし）も手抜きではない。後退は全部、固有値を渡されず推測で書いた小部品（タブ間・タグの padding と weight・重なりの前後とずらし量・表の列幅・重なったアバターの誤読）で、汎用の知見が「値」を運べないことの表れ。汎用知見だけで直せるのは「測る手順」なので、各項目の確認手順をターン内で実行したかで判定する。
断片ごとの layoutDiff を前回最良と比べ、10 倍悪い断片があれば、その断片を参照と並べて見直す。
**対策**:
- 同じターゲットに前回の成果物があるなら、書き始める前に**前回最良の最終成果物から**図形の path・アイコン・ロゴ・一致していた行（タブ行・ヘッダー）の値を持ってくる。描き直さない
- **持ってくる元は最終成果物だけ**。作業ディレクトリの途中版・試作ファイルは後退版のことがある（後退版を丸ごと写して「速く」なった回があった）
- ただし持ってくる前にその部品を参照と scan で比べ、前回最良が CSS 2 以上外れている部品は参照から作る
- **持ってきた部品は、持ってきた部分のずれも引き継ぐ**。固有ファイルの「実装」列にある既知のずれは、持ってきたあとで直す
- 書き直すなら、行の最後の要素の ink 右端を横 scan して前回最良と比べる
- 高さを倍率（scale）で伸ばすときは上端を固定し、上の padding は動かさない（倍率と padding を両方動かすと上端がずれる）
- isolated で前回最良を読めない回は、ターゲット固有ファイルの値で書く。推測で既定値を書くと毎回同じ所で外す
- 仕上げでは、layoutDiff が閾値を切っていても、ヒーローの輪郭やロゴなど前回壊れた場所だけは参照と並べて測る

### line-height は行ピッチを実測して px で書く
**観察**: 行間が 1〜2.5px 広いだけでも、5〜6行積むと 10px 以上ずれてブロック全体が下にずれた。
リスト行の padding の推測値が 1行あたり CSS 1〜1.5 長く、5本目の区切り線で CSS 6 以上ずれた。
段落間の余白も、行ピッチは合っているのに `mt` の推測値で段落の頭がずれた。
**対策**: 複数行のテキストは `leading-[21px]` のように px 指定する。倍率指定は font-size を変えるたびにピッチが動くので使わない。
リストの行送りは**区切り線→区切り線**で測る。段落の余白は `段落間の ink 上端差 − 行ピッチ` で出す。

**観察（UIキットの 14px 文字は行箱の中で CSS 1.5〜2 上に出る）**: 行の高さ・入力欄・アイコン・行ピッチは一致しているのに、文字の ink 上端だけが上に出る現象が同じ系統のターゲットで5回続いた。
judge は「ページ全体が上」「ラベル→入力の間隔が短い」と書いたが、**箱は一致していて文字だけが上**で、方向も逆だった。ページ全体を下げると箱がずれる。
**対策**: UIキットの 14px / 22px 行の文字は、書いたら1か所 ink 上端を参照と比べる。CSS 1.5〜2 上なら、行の高さ・gap・アイコンは動かさず、
**文字の span だけ** `relative top-[2px]`（ラベルなら `pt-[2px] pb-[6px]`）で下げる。行ごと動かすとアイコンと子メニューが逆にずれる。
ヘッダーのユーザー名・ロゴ文字にも同じ下げを当てる（メニューだけ直して残した回があった）。

### 角丸・円は外形を画素で数える（角丸は左端の食い込み、円は直径）
**観察（角丸）**: サムネの角丸が参照の半分だった。上端の行から下へ順に左端を見ると、食い込みの画素数で差が出る。
**対策（角丸）**: `pnpm probe pair <参照> <実装> <角の座標> 40 40 --scale 8` で角だけを並べて拡大し、食い込みの画素数を数える。CSS px はその半分（@2x）。
**観察（円）**: judge は「ベースラインが約6px 下」と報告したが、原因は行の padding ではなく**円が 6px 大きいこと**で、行の高さが押し広げられていた。padding を削っても直らない。
**対策（円）**: 丸い要素は、中心を通る横1行を scan して左端〜右端の画素数を数える。行のずれを見つけたら、まずその行の中で一番大きい要素（アバター・ボタン）の寸法を疑う。

- **アバター横の文字ブロックを center で置かない**: 文字ブロックがアバターより高いと、`self-center` が行を押し広げ、アバターは合っているのに名前と紹介文が下にずれた（judge は「余白を詰めよ」と書いたが原因は縦揃え）。参照で名前 ink 上端とアバター上端を縦 scan で比べ、揃っていれば上揃え（items-start）にする
- **名前の折り返しは円の直径と文字サイズで決まる**: 参照で名前が何行かを先に数え、直径 → 文字サイズの順に合わせる。1行に収まってしまったら、どちらかが違う合図
- **参照にないイニシャル文字を足さない**（写真のアバターに Fallback のイニシャルを出すのは省略）
- **重なった円の並びは「中身・前後・ずらし量」の3つを測ってから書く**:
  **観察**: 円の右下の小さな色の塊を「ステータス点」と読み、飽和した単色の小円（緑）で描いた回が3回あった（run 02-56-01、12-57-50、15-58-08。12-57-50 はこの項目を読んだうえで再発）。参照の塊は淡い灰緑の地に升目のある2つ目のアバター（identicon）で、中を縦 scan すると明度が 177 と 247 で交互に変わる。実装の単色は 1 区間で終わる。
  前後関係も2回外した（run 12-39-35、12-57-50）: `-ml-*` を DOM 順のまま使うと右の円が上になり、参照（左が上、1個目の identicon が全部見える）で幅 64 見えるところが 30〜40 しか見えなかった。ずらし量も推測値（直径 32 に `-ml-3`）で、参照の送り 13 に対して 20 になり、後ろの「+ 件数」の左端が元画素 40 右へ出た（run 12-57-50）。judge は「重なりが小さい」とだけ書いた。
  **対策**: (1) 小さな円は `probe scan --x` で中を縦に通し、区間が1つ（単色）でなければアバターとして描く。ステータス点だと思ったら、地の色が飽和しているかを `probe color --r 0` で確かめる。淡い・升目がある・人数の文言と数が合うなら点ではない。(2) 1個目の中心を通る横 scan で、1個目の色が次の円の左端より右まで続くなら左が上 → `relative` ＋降順の `z-index`（または `flex-row-reverse`）。(3) ずらし量は「円の左端のピッチ」と「最後の要素（「+」の文字）の左端」を参照で測り、`-ml-*` は `直径 − ピッチ` で決める。書いたら「+」の左端を scan で突き合わせる。(4) **円の個数を数える**: 知見なしの回（run 16-25-24）は参照 5 個の重なりを 4 個で描き、送りは参照より広いのに群れが短く、「+」が元画素 19 左に出た。judge は「重なりが小さい・群れが狭い」と書いたが、原因は個数。横 scan で円の区間の数を参照と数えてから送りを決める
- **grid・flex の中の円は `block` か `flex` にする**: `inline-flex` / `inline-block` だと行ボックスの下に字の下がりぶんが足され、グリッドの行が1行あたり数 px 押し広げられた（judge は「行間を詰めよ」と書いたが、gap を詰めると列の間まで狭くなる）。並べたら縦 scan で円の上端のピッチを測り、`直径 + gap` と一致するか確かめる

### 見出しの下の「見出し下端 → 区切り線」を測る
**観察**: セクション見出しの ink 下端から下線までが参照の倍近くあり、下線が下がって、その下の要素が全部ずれた。
共通の見出し部品にこの誤りを入れると、全見出しに複製され、下の見出しほどずれが溜まった。
リスト行も1段目は合っていて、2段目（1行の説明文の行）の行高が短く、次のセクションが詰まった。
本文カラムの見出しに padding-left がなく、本文の先頭 ink より左に出た回もあった。
**対策**: セクション見出しは「文字サイズ」より先に「見出し下端から次の線・次の要素までの距離」を測る。ここは縦の積み上げの起点なので、外すと下が全部ずれる。
共通の見出し部品を作ったら、1つ目の見出しで ink 下端 → 線を `scan --x` で測ってから他に使う。リスト行は1行目だけでなく**2行目の線→線**も測る。
本文カラムの見出しを置いたら、見出しの先頭 ink と本文（字下げのない行）の先頭 ink を `scan --y` で比べ、揃っていなければ padding-left を足す。

### 単色ブロックは「写真だけ」。平均色の表を見ても文字入りサムネは潰さない
**観察**: サムネを「見た目の主色」の単色ブロックで置くと、参照の平均（白地と文字が混ざって彩度が低い）より派手すぎた。
また、知見に平均色の数値を並べたら、それを**そのまま単色ブロックに貼られた**。平均色が載っていたことが「単色でよい」合図として読まれた（judge に dropped で不合格）。
書影の文字だけ描いて、軸・バッジ・帯などの図形を落とす型もある。文字を描いたことで「中身は描いた」と判断して止まる。
アバターの列も「写真」とは限らない。5×5 の升目の自動生成アバター（identicon）は描けるのに、judge が「写真なので軽微」と書いて減点しなかった。
**対策**: まず中身を見て、文字・図形が1つでもあれば描く（下の「再現しないのは描けないもの」の表に従う）。
書影・サムネは**文字を描いたあとに、文字以外の図形（軸・バッジ・帯）を数えて**参照と個数を合わせる。
アバターは1個ずつ見て、市松・十字の升目なら identicon として 5×5 の grid で描く。単色の円にしてよいのは人物の写真だけ。judge が「写真」と呼んでも identicon は含めない。
平均色は、写真の人物部分や、描いた図形の**地の色**を決めるときだけに使う（`pnpm probe color <参照> <中心x> <中心y> --r 30`。layoutDiff はぼかし後の比較なので広い半径の平均が効く）。
**帯付きサムネのキャプション**: 帯の中の文字とロゴを横に並べたら、幅に収まらず折り返して帯の外にあふれ、切れた回があった。帯の中は `whitespace-nowrap`、ロゴは `shrink-0` の小さな図形（文字で書くなら参照の ink 幅以下）にし、帯色と文字色はそれぞれ測る。描いたら帯の下端を縦 scan し、帯の外に文字の ink が出ていないことを確かめる。

### 直したら同じ座標を測り直す
**観察**: 5ターン回して色も文字サイズも合わないまま収束した回があった。「直したつもり」で次のターンに進んでいた。
また、brain が「次のターンで直す」と書いた知見違反が、1ターン目で閾値を切って収束したため、そのまま残った。**収束すれば次のターンは来ない**。
**対策**: 1ターンの終わりに、そのターンで触れた箇所だけ `probe color` / `probe pair` で参照と実装を測り直す。数値が一致しない修正は、その場で直す。
知見への違反に自分で気づいたら、「次のターン」と書かずに、そのターンのうちに builder へ直させる。

### `palt` を見出し全体に掛けない。約物だけ詰まっているなら約物だけ span で詰める。折り返しと字下げは参照どおり明示する
**観察**: 複数行のタイトルに `palt` を付けると、かなも詰まり、1行に入る字数が変わって折り返しがずれた。
逆に「palt を入れない」だけを渡すと、参照で約物（【】「」、）が半角に詰まっているタイトルでも詰めなくなり、太字タイトルの折り返しが全部ずれた。
全体に掛けるか掛けないかの二択にせず、約物だけを `<span className="[font-feature-settings:'palt']">` で包むと、字数も折り返しも一致した。
**対策**: 太字タイトルは書く前に、参照の1行目の字数を数え、行頭の括弧の ink 左端がテキスト枠の左端から半字ぶん入っていないか見る。入っていなければ約物が詰まっているので、約物だけを palt の span で包む。
参照で約物が詰まっていない本文には palt を一切付けない。

- **`<br />` は「ここで折る」は保証するが「ここまで入る」は保証しない**: br の前で自動折り返しが起きて1行増えた回があった。br を入れたら、撮った断片でその段落の行数を数える。1行多ければ br を増やさず、約物 span か枠幅で1行目に入れる
- **`whitespace-nowrap` を付けると、あふれても折り返しでは気づけず切れるだけになる**。付けたら1行目の ink 右端が枠の内側に収まっているか scan で確かめる。狭いサイドバーで、推測で1段大きくした太字タイトルに nowrap を付けたら、後ろのバッジが列の区切り線の右端より元画素 42 外へはみ出した（run 12-09-04）。はみ出しを見たら nowrap を外す前に、まず font-size を ink 高さで確かめる
- **折り返しが1字ずれたら、先に字の大きさを比べる**。字の ink 高さ・送りが一致するなら、font-size や tracking を触らずに**枠の右端**を scan で合わせる
- **ただし、段落を包むコンテナの padding で折り返しを合わせない**: 環境のフォント幅差で折り返しがずれたのを、本文コンテナの右 padding を CSS 32→28 に減らして合わせた回があった。コンテナの中の区切り線・コードブロックの枠の右端がすべて元画素 8 右へ伸びた（run 12-09-04）。judge はこれを「右 padding が狭い」と指摘した。枠を共有する要素（hr・見出し下線・pre の枠）があるコンテナの padding は、左右とも参照の値のままにする。折り返しは、その段落だけに `max-w` を付けて合わせる。変えたら、同じコンテナにある区切り線の右端を横 scan する。judge が「本文カラムが数 px 狭く1語早く折り返す」と書いた回も、見出し下線の右端・枠線は参照と同じ元画素で一致しており、原因はフォント幅だった（run 12-57-50）。枠が一致していれば幅を触らない
- **枠と字の大きさが両方わずかにずれると、palt を付けても1字あふれる**。前回最良が一致していたなら、幅・font-size・line-height の値を3つ揃えて持ってくる（1つだけ持ってきても外れる）
- **写っていない行を作文しない**: 断片の境目で中間の行がどの断片にも写っていない段落を自作の文で埋めると、最終行の字数が変わり、後ろの断片で外れる。前回最良の文をそのまま使い、最終行を後ろの断片で確かめる
- **中央に置かれたブロックを `self-start` + padding で寄せない**。中央寄せにして、1行目の ink 左端を scan で確かめる
- **アイコン付きタイトルを flex で組むと2行目が字下げされる**: 行頭のアイコン（鍵・バッジなど）を flex の兄弟にすると、タイトルが1つの flex 子になって2行目がアイコンの右から始まる。テキストと同じインライン流しに `inline-block` + `align-[-2px]` で置き、2行目の ink 左端が1行目のアイコン左端より左にあるか scan で確かめる
- **行頭の全角スペースは JSX で消える**: 開始タグの次の行に書いた行頭の全角スペース（U+3000）は JSX の行頭空白として削られた。`{'　'}` で書くか開始タグと同じ行に置く。段落全体の字下げなら `indent-[1em]`。書いたら字下げした段落の先頭 ink 左端を測り、カラム左端と同じなら消えている

### Read で見た画像は縮小されている。座標は表示上の値のまま使わない（参照が @2x なら、測った元画素は2で割る）
**観察**: Read は大きな参照を縮小して表示する（幅 2940px なら 2000px に。表示上の 1px は CSS 0.735px）。縮小表示から座標を読んだとみられる回で、小さな要素が CSS 100px 以上ずれた。judge が書く座標も縮小表示の値のことがある。
**対策**: 位置は画像を見た目で読まず、`probe grid` か `probe crop` で**元画素の座標**を得てから倍率で割る。
Read の表示で読んだ座標を使うなら縮小率を掛けて戻す。
**倍率の確認**: 高さの分かっている要素（ボタンなど）を参照と自前出力（DPR 既知）で scan し、CSS 換算が成立するか確かめてから測る。

### 固定幅・固定 margin に小数 px を入れない。flex/absolute を使っていても座標のなぞりになる
**観察**: absolute を減らしても、`ml-[222.5px] w-[1024.5px]`・`h-[97.8px]` のように測った座標を固定値で流し込むと、judge に「座標をなぞった値」と指摘されて不合格になった。
整数でも、横並びのパネルを全部固定幅で置くと同じく「可変レイアウトになっていない」と指摘された。フォームの列を固定 px で置くと「狭い画面で比率を保てない」と指摘された。
**対策**: 小数を含む値（`.5` `.8` `.25`）を left / margin / width / height に書いたら、座標を写していないか疑う。
コンテナは `mx-auto max-w-[N]`、カラム間は gap、行の高さは中身・padding で決める。小数を残してよいのは線の太さや 1px 未満の微調整だけ。
**横並びのうち1列は `1fr` にする**。UIキットのグリッド（24分割など）で組まれた画面は、測った列の左端から行幅を逆算して span / offset に直してから書く。px の列幅は確認に使う。

### 共通のパネル部品の誤りは全パネルに複製される。部品を作ったら1枚だけ測ってから並べる
**観察**: 共通部品の基底クラスに `items-start` を書き、呼び出し側から `items-center` を足したら、CSS の出力順で基底が勝ち、全パネルの見出しが同じだけずれた。judge は拾わなかった。
同じ部品のスクロール領域を常時つまみ表示にし、参照に無いスクロールバーが全パネルに出た。
繰り返すリストの1件の送りが CSS 数 px 短いだけで、4件目では 20px 以上ずれた。
**対策**: 部品の className に、基底と同じプロパティ（items-*・justify-*・p*・h-*）のクラスを渡さない。変えたい値は props（`align="center"`）で受ける。
スクロール部品は、参照につまみが写っていなければ `type="hover"`（または scrollbar を描かない）にする。
部品を作ったら、並べる前に1枚目の見出し位置を縦 scan で参照と比べる。
繰り返す行は、1件目ではなく**区切り線から次の区切り線まで**を測り、その送りを行の padding で合わせる。

### 横並びの部品は、ずれた部品ではなく隣と群れの端を測る
**観察**: 右寄せのボタン群で、右端はそろっているのに左の部品が右にずれていた。原因は右端の部品（文字＋間＋アイコン）の幅が参照より少し足りないことで、その不足がそのまま左の部品を押していた。
検索欄が「広い」と言われた回も、欄の幅は一致していて、右隣のボタンが広いぶん左へ押されていただけだった。
入力欄の中のアイコンを、欄の兄弟に負 margin で重ねると、欄そのものが広がった。
日付範囲の入力で、区切りの矢印を左右対称の margin や `flex-1` の等分で置いたら、参照は矢印の前後の余白が非対称で、2つ目の日付がずれた。
この型は同じ行で5回再発した。どの回も原因は gap・margin・padding の**推測値**で、judge は場所だけ当てて原因（塊の中が広い／塊の間が狭い、の打ち消し合い）も方向も外した:

- 4回目（run 16-36-12）・5回目（run 16-11-36）も知見なしで同じ形: タブ `px-2 gap-2` の推測で、アイコン→ラベル 26→21、同じ画面の2つ目のタブ列でも 22→19。1タブあたり元画素 5〜8 ずつ溜まり、右端のタブが 24〜48 左。2つ目のタブ列は塊の間も 51→36 と狭く、右端が 91（CSS 45）手前で終わった。judge はどちらも「タブ間が狭い」と書き、量は CSS 13〜30 と**過小**だった。この行のずれは毎回「アイコン→ラベル」から始まる。**アイコン付きのタブ・ボタンを並べたら、最初の1個のアイコン ink 右端→文字 ink 左端を参照と比べてから残りを並べる**

- 同じ回（15-41-44）、右寄せのボタン3つがそれぞれ外幅で元画素 14〜20 狭く（文字＋padding で幅を作った）、左端のボタンが 50 右へ押された
- truncate する文言の後ろの `ml-4`・セルの `pr-4` で、文言の切れる位置が元画素 16〜60 早まった（run 12-19-34、12-57-50）
**対策**:
- 右寄せ・左寄せの群れは、端の部品だけでなく**反対側の端の部品の端**も測る。ずれたら、揃っている側の部品の幅を参照の ink と比べ、足りない分を足す
- **手順（ターンを終える前の必須の確認。飛ばした回で毎回外した）**: 横並びの行（タブ行・ボタン群・タグの行・重なった円の行・truncate する列のある表）を書いたら、その行を1本横 scan（ink の塊の左端〜右端を並べる）して、参照と**塊ごとに**左端・右端を表にする。ずれが始まる最初の塊と、その直前の間を直す。右寄せ（`ml-auto`）の塊がずれていたら、その右にある塊の幅から疑う。**文字の行は `probe scan --y` では読めない**（1文字ごとに区間が切れて 300 区間を超え、途中で打ち切られる）。帯（例: 行の上端〜下端）の各列に閾値（明度 170 未満）より暗い画素があるかを見て、12px 以下の隙間をつないだ「ink の塊」の一覧を出す短いスクリプト（sharp で書ける）を使う。参照と実装で同じ帯に掛ければ、そのまま塊の表になる（run 16-36-12 の振り返りで、この方法で3画像の表を1回で出せた）
- flex の `gap` と子の `ml-*` / `mr-*` は足し算になる。間は gap か margin のどちらか1つで書き、並んだ要素の間隔は単一の gap にする。**部品に `className="ml-*"` を渡すのも同じ違反**（部品の定義だけ見ると気づけない）。書き終えたら `gap-` を持つ要素の直下の子を grep し、`ml-` / `mr-` / `mx-` が残っていないか確かめる
- 塊の表では「塊の幅」と「塊と塊の間」を別の列にする。右端が合わないとき、塊の中（ラベル→数字）が広く、塊の間が狭いと打ち消し合う。**右端だけ見て gap を足すと、中の誤りが残る**
- `truncate` する要素の直後の部品の margin は、文言の切れる位置を直接動かす。切れる位置が参照と違ったら、文言ではなく後ろの間を測る
- **切れ方は列の左端と右端の両方で変わる**: 参照では「…」で切れる文言が実装では全文出るなら、その列が広い。固定幅の1列目を推測で書き、次の列の文言の左端が元画素 67 左に出て、参照の「…」切れが全部消えた（run 15-52-00）。逆に早く切れた回（run 16-17-54）は左端が参照と同じ元画素で、右端だけ 35 手前で切れていた。原因は右の固定幅の列＋gap。judge は「1列目を緩めよ」と書いたが、それは誤診だった。表を書いたら、truncate する列の ink の**左端と右端**を1行測る。左端が合っていれば前の列は触らず、後ろの列の幅と gap を直す
- ボタンは「文字＋padding」で幅を作ると、欧文の字幅が参照と数 % 違う環境で外れる。**外幅を測って `min-w` で合わせる**。測らずに固定幅（`w-[118px]`）を推測で書いた回（run 16-25-24）は、右寄せのボタンが外幅で元画素 18 広く、左隣の検索欄がそのぶん狭くなった。固定幅でも推測なら同じ失敗なので、書く前に参照の外枠を横 scan する
- 入力欄の中のアイコンは、欄の要素の内側か `relative` の包みに入れる。兄弟に負 margin で重ねない
- 区切り記号の前後の余白は対称と決めつけず、両側を測る
- アイコンの大きさは `size` の数値ではなく **ink の外接**で参照に合わせる（同じ size でも SVG によって ink が違う）。線が細いなら size ではなく strokeWidth を上げる
- 参照で文字が欄幅を超えて末尾（コロンなど）が切れているラベルは、実装の字幅が狭いと収まってしまい末尾が出る。切れるかどうかを幅で再現しようとせず、参照で見えない末尾はそのラベルだけ描かない

## judge の指摘の読み方

### 寸法・大小の指摘は「場所のヒント」。値と方向は自分で測り直す
**観察**: judge の指摘を実測で確かめると、半分近くが外れていた。「拡大せよ」が実際は実装のほうが大きい、「gap を広げよ」が実際は実装のほうが既に広い、「サイズが小さい」が参照も実装も同寸、など。
同じ種類の誤り（ある SNS アイコンが「小さい」）は、同じターゲットで5回繰り返された。judge が書いてくるブランド色も記憶由来で、参照の実測とは違った。
judge の「約◯px」は縮小表示上の値のこともある。部品ごとのずれが溜まる行では、逆に**過小**に書く（タブ列の右端 CSS 45 の不足を「13〜30px」と書いた。run 16-11-36）。
一方で**形の違い**（アイコンの字形、角丸の強さ、中の文字の大きさ）の指摘は当たっていた。
**対策**: judge が挙げた**場所**だけを受け取り、値は probe で測ってから直す。指摘の数値・16進をそのままコードに入れない。
全体が「数 px 下」と言われたら、周りの要素（カードの上の本文など）も同じだけずれていないか測る。同じならその部品ではなく、カラム全体の padding を直す。
ずれが「どこから始まるか」を上流の区切り線から順に測る（原因は指摘された見出しではなく、その上の区画の行ピッチのことがある）。
当たるのは「並びの中で1つだけ間隔が半分」「角丸が半分」「その要素だけ中身がない・小さい」のような**相対的な異常**。judge は「相対的に変」は得意、「何pxが正しいか」は苦手、と割り切る。

### layoutDiff が閾値の 1/10 未満になったら、judge の指摘は「場所は当たり、値と直し方は半分外れる」。直す前に全件測る
**観察**: layoutDiff 0.00% の段階では、judge は字形の差（システムフォントの約物の広さ）を寸法のずれとして言い換える。
5件とも実装が参照と一致、または逆方向だった回もあれば、場所は5件とも当たりで原因と量が外れた回もある。同じターゲットでも run によって当たり外れが入れ替わる。
明度・色の指摘（「白寄り」「薄い」「濃い」「この色に」）は、連続して方向が逆か誤差だった。judge の書いた16進が参照のどこにもないこともあった。逆に「わずかに薄い（minor）」と書かれた色が、不透明度の段が違う大きな差だったこともある。
「字形の差なので minor」と片付けられた差が、実は font-size の誤り（ink 幅が 84%）だったこともある。
**対策**:
- 指摘の信頼度を前回の judge から持ち越さず、コードを触る前に**全件**を元画素で測る。差が 1 CSS px 未満なら直さない
- 差が実在したら、judge の書いた原因ではなく、測って特定した1か所（gap・margin・幅の1値）だけ直す
- 「大きく太い」「広い」は ink の**幅と高さを別々に**測る。幅だけ広く高さが合う（または低い）なら font-size ではなく weight か字送りの差
- 「細い・太い」は外接矩形では出ない。同じ矩形の**暗画素数**（明度 110 未満）を参照と数え、比が 0.9〜1.1 を外れたら weight を1段動かす
- 色・明度の指摘は、同じ座標を `probe color` で両方測る。明度差が 3 以下なら直さない。方向も測った値で決める
- 「字形の差」と書かれた指摘も ink 幅を測り、参照との比が 0.95 を下回るなら font-size を疑う。**ただし1語だけで判断しない**。同じ font-size でも語で比がばらつくので、3語以上測って比がそろって 0.95 未満のときだけ動かす
- 「列が狭い」「1行少ない」「折り返しが違う」と言われたら、列幅や leading を触る前に1行目の ink 幅と行ピッチを比べる。ピッチが一致して ink 幅が 3% 以上広いなら font-size（同じ誤診が2回続いた）。`<br>` や leading で直すとピッチが外れる
- 1件見つかったら、judge が挙げなかった同じ font-size の文字も全部測る
- 自分で測るのは「ink の左右端・上下端」（暗画素が出る列・行の範囲）。見た目の余白の印象では判断しない

### blocking・dropped の指摘も、最終スクショを自分で読んでから扱う。judge は中身の欠落を拾わない
**観察**: 「〜が画面に出ない（blocking）」が同じターゲットで4回外れた。最終の断片画像には写っていた。judge はコードの overflow 指定を読んで「スクロールできない＝出ない」と推論していた。表の値が違う、合計が違う、という blocking が事実無根だったこともある。
逆に、リストの先頭1件の欠落、サムネの中身の省略、ロゴの字形違い、sticky 列の押し上げの放棄は、5件のどれにも出ないか「minor」「状態の違い」で済まされた。judge の「画像ソースがないので減点しない」も鵜呑みにできない（描けるものが含まれていた）。
**対策**: blocking でも、値やテキストの食い違いは最終スクショを自分で読んでから扱う。
dropped を judge に任せず、断片ごとの項目の先頭タイトルやアイコンの中身を自分で照合する。judge の件数が埋まっていても、ロゴとナビ先頭の左端は自分で scan する。
judge の点数（80点台後半〜90点台）で良し悪しを決めない。
judge が「状態の違い」とひとまとめにした指摘は分けて読む（直すべき列の位置と、直さないトグルの押下状態が同じ1件に入っていた）。

## 再現できないもの（時間を使わない）

### 再現しないのは「描けないもの」だけ。画像の中の文字は描く
**観察**: 「画像は単色ブロックで置く」を**画像領域ごと**に適用して、大きな文字の載ったヒーローを1枚の矩形にした回があった。
layoutDiff も judge も劣化を検出できず、前の試行が再現できていた文字を失う後退になった。
写真の中のスマホ画面に写った文字や、サムネの中の白抜きの横顔を、単色で潰す省略は同じターゲットで8回続いた（知見のない回ほど毎回）。
**対策**: 判断基準は「画像かどうか」ではなく「**文字や図形として描けるか**」。

| 参照にあるもの | どうするか |
| --- | --- |
| **チャート（棒・折れ線・エリア・円・スパークライン）** | **SVGで描く**。単色ブロックで潰さない |
| 写真（人物・風景・商品） | 広域平均色の単色ブロック。寸法・角丸・位置は合わせる |
| イラストの絵の部分（シルエット等） | 単色ブロック、または近い形の図形 |
| **画像の上に載った文字** | **文字として描く**。潰さない |
| **写真の中の画面（スマホ・PC）に写った文字**、サムネ内の白抜き図形 | 描く。画面の部分は写真扱いしない。暗い斜めの板＋白い小さな文字1行で足りる。見出し文字だけ残して図形（軸・スタンプ・シルエット）を落とすのも同じ省略 |
| ロゴ | 字形は合わないが、**文字として置く**。空の矩形にしない |
| 直径40px以下のアイコン・アバター（イラストのアバターを含む） | 中の白いマークまで文字か簡単なSVGで描く |
| 幾何模様のアバター（升目の自動生成アイコン）、バッジ・ボタンの中の小さなロゴ | 描く。升目は 5×5 grid、ロゴは簡単な SVG。空の円・ロゴなしにすると部品の幅も縮む |

大きな領域を中身のない矩形1枚で埋めたら、それは手抜きを疑う。

**うまくいった描き方**: ヒーローもサムネも、外枠を `grid` にして子を全部 `[grid-area:1/1]` で同じセルに重ね、
padding で位置をずらして文字・SVG（シルエットの path、小さな図形、アイコン、ロゴ）を載せる。
absolute を使わずに「画像の中の重なり」を表現でき、absolute 比率が低いまま layoutDiff も下がった。サムネはヒーローと同じ部品を縮小して再利用できる。
judge が「文字を pt/pl で置いている」と書いても、この書き方なら構造の退化ではない。
縦書きの文字を並べたカードは、1列に収まる幅を先に決める（細すぎて2列に折り返した回があった）。

**収束の速さと judge の点数は、中身の量を保証しない**: 知見なしの回は、速く収束して judge も高い点を付けたが、前回最良と並べると、キャラクターの図形が単純な楕円に、写真のアバターがイニシャル円に、サムネの表や凡例の文字が消えていた。構造の指標も judge も、この退化を検出していない。前回最良の turn png と並べ、描いた要素の数を比べる。
同じ型は別ターゲットでも出た（run 15-41-44: layoutDiff 0.00%・2ターン・judge 88〜92 で収束したが、前回最良が描いていた幾何模様のアバターが全部単色の円、バッジの左端の小さなロゴが欠落してバッジ列が元画素 72 短く、バッジ色はバッジサービスの既定値）。layoutDiff 0% は「中身が揃った」ことを意味しない。
**対策**: アバターやアイコンを `rounded-full bg-…` の空の円で書いたら、参照でその円の中にマークがないか crop で見る。あれば SVG の path か文字で描く。
Radix `Avatar.Fallback` にイニシャルを入れるのも同じ省略。参照がイラストなら SVG で描く。
サムネは題字を描いたあとで、枠・バッジ・シルエットが残っていないか数える。
アイコンは描いても**大きさを推測すると半分になる**。描いたら行ごとの ink 外接矩形を参照と比べる。

### 断片ごとに列の見える範囲が違うなら、sticky 列の押し上げで両立させる（多数派に合わせて止めるのはトグルの押下状態だけ）
**観察**: 参照がスクロールショットの集まりで、ある断片だけ操作で変わる装飾（押されたトグル）が写っていることがある。これは1つの状態では両立しないので、どちらかに合わせるともう一方が外れる。
一方、ある断片だけ右コラムや左の目次が「押し上げられて」別の範囲が写っていることもある。これは**1つの状態で両立できる**。
古い知見が「状態が違う部分は合わせない」「多数派の断片に合わせて止める」までしか書いていなかった版を渡すと、押し上げまで「再現しない」と決めて、同じ所を6回続けて捨てた。
知見がなくても、「ビューポート高の内部スクロール容器を作らない」検査を避けて `overflow-clip` や高さ短縮に逃げると、同じく押し上げを捨てる方向に落ちた。
「body だけでスクロールする制約では再現できない」と書いて止めた回もあったが、同じ制約のまま両立させた回がある。
**対策（トグル）**: 押下状態のように1つの状態では両立しないものだけ、参照の多数派の断片に合わせて止める。スクロール量に応じて状態を切り替えたり、コラムを scrollTop で動かしたりしない。
**対策（列の見える範囲）**: 内部スクロール容器（overflow-y-auto・ScrollArea）ではなく、**高さ無制限の sticky 列 + 外枠下端での押し上げ**で両立させる。
- sticky 列（右のコラムも左の目次も）は、ページ後半の中身（リストの末尾・パンくずなど）まで含む**同じ外枠の直下の子**にして `sticky top-[ヘッダー高] self-start` で置く。外枠の下端に押されてページと一緒に上へ進む。右だけ直して左を内側の包みに置き忘れた回があった
- 列の下に固定する保存バーなどは列から外して `fixed bottom-0`
- 列や目次に `h-[calc(100vh-…)]` を書いたら、それは押し上げを捨てた印
- 押し上げが**足りない**ときは、コメント本文や余白を触らず、まず外枠の中の件数（リストの項目数・1件の送り）を参照と照合する（1件の欠落が別の列のずれとして出た）。**行き過ぎる**ときは、列の中の件数を照合する（参照に無い項目を創作して行き過ぎた回があった）。参照の本文は一字も削らない
- 組んだら、押し上げのある断片とない断片の両方で、列の中の目印（名前の ink 上端など）を縦 scan して参照と比べる
- 中身は落とさない。参照に写っている項目は全部データに入れる
- ScrollArea が期待 primitive なら、背の低い要素（パンくずの横スクロールなど）に1ターン目から置く。Viewport の overflow をインラインで上書きして検査を通そうとすると、ターンが往復で溶けた。中身のない包みで数合わせもしない

### チャートは SVG で描く。画像として潰さない
**観察**: ダッシュボード系の参照は、棒グラフ・折れ線・エリアチャートが画面の主役を占める。これは写真ではないので単色ブロックで潰すと画面の中身がごっそり消える。かといって画像素材も無い。
**対策**: **SVGで描く。** チャートは座標と図形の集まりなので、参照から読み取って再現できる。

手順:
1. `probe scan` でプロット領域の上下端・左右端を取る（軸線は明度が変わるので帯として出る）
2. 棒グラフなら各バーの左端・幅・高さを `probe scan --y <ベースライン>` で横に走査して読む
3. 折れ線・エリアなら、数点だけ `probe scan --x <x>` で縦に走査して y を取り、その間を結ぶ
4. 目盛りラベル・凡例は**文字として描く**（画像の中の文字と同じ扱い）
5. `<svg viewBox>` に `<rect>` `<path>` `<line>` で置く。ライブラリは入れない

値を1つずつ厳密に合わせる必要はない。**本数・向き・おおよその高さ・色**が合っていればぼかし後の比較では十分に一致する。逆に、のっぺりした矩形で埋めると大きく外れる。

- **画面下端で切れている要素も落とさない**: 下端で上半分だけ写っていたラベルが、実装では位置がわずかにずれて画面外に押し出されて消えた。ぼかし後の差が小さく layoutDiff 0.00% でも通る。組んだら画面の**下端の 40 元画素**を横 scan し、参照に ink がある列に実装も ink があるかを確かめる
- **円グラフの中心と半径を推測しない**: 2回とも推測して、方向も値も違う所にラベルが出た。`cx/cy/R` は書く前に外周の上端・左右端を scan して決め、引き出し線の水平部の y を参照の縦 scan と合わせる
- **軸線は「見えるか」から測る**: 参照の軸線はほぼ白で最後の棒の手前で終わり、代わりに各棒の下に短い目盛りがあった。軸を書く前に、棒の間の列とベースラインの下を縦 scan して、線・目盛りの色と端を取る
- **画面外に続く文章の量は、中央揃えの隣の要素の位置に出る**: 画面下端で切れる本文を見えている行で終わらせたら、隣の中央揃えのサムネが上にずれた。その要素の上端を scan して、合うまで本文を画面外に足す（行数 = ずれ × 2 / 行ピッチ）

### フォントの字形は一致しない
**観察**: rawDiff がある値から下がらない。参照は Web フォント、実装はシステムフォントなので、文字が正しい位置にあっても全ピクセルが不一致になる。
参照は括弧・約物が詰まることがある（全角幅の半分程度）。字送りは完全には合わない。アイコンの字形（アイコンセットの違い）も直す対象ではない。
**対策**: `rawDiff` は見ない。`layoutDiff`（ぼかし後）で判断する。
合わせるのは **ink 高さ・ウェイト・行ピッチ・行の折り返し位置**の4つだけ。

### 寸法は `probe scan` で「帯の太さ」として読む（grid / crop / pair は場所探し用）
**観察**: judge の指摘は「約4%拡大」「約6pxずれ」と全部が概算で、そのまま直しても合わない。グリッドを重ねて座標を目で読む方法は、目盛りの間で読み違える。
scan でボタンの高さを測ると `位置 / 太さ / 明度` が一桁まで確定した。
**対策**: 高さ・幅・余白・罫線の位置は scan で読む。直線上を走査して「同じ明度が続く区間」を並べるので、要素の境界がそのまま数値になる。

```sh
pnpm probe scan <画像> --x 900 --from 1180 --to 1300    # 縦に走査（高さ・行の位置）
pnpm probe scan <画像> --y 1240 --from 400 --to 2000    # 横に走査（幅・左右の余白）
    [--tolerance 6]   まとめる明度の幅。細部を見るなら下げる
    [--min 2]         この太さ未満の区間を隠す。ノイズが多いとき
pnpm probe grid <参照> --step 100                          # 場所の見当をつける
pnpm probe pair <参照> <実装> <x> <y> <w> <h> --scale 2     # 上=参照 下=実装
```

読み方: `位置1220 太さ80 明度115` = y1220 から 80px の帯。参照が @2x なら CSS では y610 から高さ40px。
参照と実装の**同じ座標**を scan して並べると、ずれが数値で出る。judge の概算を、そのまま信じずに検算できる。

シェルは zsh。`for p in "1100 1150"; do pnpm probe color $f $p` は座標が1つの引数のまま渡り、**何も出さずに exit 1** になる。
ループで座標を回すときは `${=p}` と書くか、x と y を別の変数にする。

**観察（罫線の太さは読めない）**: 参照の罫線を縦に走査すると純白に戻らず段階的に明るくなる（圧縮のリンギングか影）。自前の出力はくっきり2px。
**対策**: 罫線の**位置**は scan で読むが、**太さ**は参照から読まず CSS 1px（@2x なら2px）を既定にする。3px 以上に見えても影かリンギング。

## 構造（なぞらない）

### 絶対配置で座標をなぞらない。flex / grid で組む
**観察**: `absolute left-[N px] top-[N px]` で要素を並べた回は、1ターンで「収束」したが、それは**ピクセル差分に最も速く到達する方法が座標でのトレースだから**であって、UIが良くなったからではない。
計測ツールで座標を測れるようになった結果、測った座標をそのまま absolute に流し込む書き方に寄った。
**対策**: 位置は親の余白・gap・サイズで表現する。絶対配置は、参照でも重なっている要素（バッジ、オーバーレイ）だけに使う。
絶対配置の比率が上限を超えると、ピクセルが合っていても収束しない。
測った値は、組んだレイアウトが合っているかの**確認**と、レイアウトの変数（カラム幅・gap）を決める材料に使う。

### 画面を並べて「ページ」に見せない
**観察**: 参照が同じページのスクロール違い数枚だったとき、ビューポート高の内部スクロール容器を枚数ぶん縦に並べ、それぞれを scrollTop で別の位置までスクロールさせた回があった。
断片の指標は全部合格したが、実際にスクロールするとヘッダーが何度も現れ、セクションが途中で切断されていた。1本のページではなく、コンタクトシートだった。
**対策**: 参照がスクロールショットの集まりでも、成果物は**1本のドキュメントフロー**にする。
- ヘッダーは1つだけ。sticky で追従させる
- ビューポート高の内部スクロール容器を作らない。スクロールは body が持つ
- scrollTop をコードから書き換えない
- 断片ごとにセクションを複製しない

DOMを検査して落とす（`header` の数、ビューポート高のスクロール容器の数、ドキュメント自身がスクロールするか、高さがビューポート高の整数倍か）。

### 数字が動かないときは、まず計測を疑う
**観察（撮影条件の違い）**: layoutDiff が10ターン動かず、エージェントの限界に見えたが、原因は計測側だった。
参照は実際にスクロールして撮られているので sticky ヘッダーがどの断片にも写る。一方ハーネスはフルページ撮影の1枚から切り出しており、sticky 要素は本来の位置に1回しか描画されない。上端の帯が永久に不一致で、それが床を作っていた。撮り直したら閾値未満になった。
**対策**: 参照と**同じ条件**で撮る。参照がスクロールして撮られたものなら、実装も同じ位置までスクロールしてビューポート撮影する。切り出しで代用しない。
スコアが複数ターン凍りついたら、実装ではなく差分画像を見る。不一致が特定の帯（上端・下端）に集中していたら、撮影条件の違いを疑う。

**観察（断片の位置合わせが全部 offset 0 に潰れる）**: 参照の各断片で sticky の要素が画面の半分以上を占めると、フルページ画像にそれらが写るのは最上部だけなので、どの断片もページ先頭に吸い寄せられ、全断片が「ページ先頭のスクショ」と比べられた。
正しい位置で撮り直して採点すると、全部閾値未満で本当は収束していた。しかもこの計測は**中身を削ると得をする**（記事冒頭を持たない後退版のほうがページ先頭が次の断片に似て良い数字が出た）。
**対策**: 毎ターン metrics の `slices[].offset` を見る。**2枚以上が同じ offset**（特に全部 0）なら、そのターンの layoutDiff は無効。
参照の断片ごとに手動のスクロール位置で撮って採点する（`captureResilient` に `{type:'scroll', y}` を足す形）。
ハーネスの数字を下げるために、冒頭を消す・sticky をやめる・ページ先頭を次の断片に似せる、はやらない。手動採点が閾値未満になったら、その数値（断片ごと）を報告して手を止める。
直すものがなくてコードを変えなかったターンの出力が減るのは、手抜きではない。

**観察（成果物の取り違え）**: 最終成果物の中身が別ターゲットの画面で、渡された構造の指標とも brain の記述とも合わなかった回があった。同時に走った別の試行と上書きし合ったとみられる。
**対策（振り返り側）**: 最終成果物を読む前に、ターゲット固有の語（人名・見出しの語）を grep する。0件なら、そのソースと構造の指標は採点に使わず、断片画像を probe で測って判定する。

## 進め方

### 1ターン目で骨格を決めきる。2ターン目以降に直すのは3〜5件
**観察**: layoutDiff は1ターン目で大半が落ち、残りのターンではわずかしか動かなかった。全部直そうとしたターンは、どれも中途半端に終わった。
**対策**: 1ターン目はカラム幅・カラム間・主要ブロックの位置と高さに全部使う。骨格が外れていると以降のターンが全部やり直しになる。以降のターンは差分の面積が大きい順に3〜5件へ絞る。

### 左下にURLのステータスバーが写っている断片は、ホバー中。その1か所の下線を常時の装飾にしない
**観察**: 断片の左下にブラウザのリンクホバー表示（URL）が写っていて、その断片ではリストの1件・名前の1つだけに下線がある。これを常時の装飾と読んで、リスト全件に `underline` を付ける誤りが、知見のない回で毎回（6回）出た。
土台にしたコードに `underline` が残っていて、それを引き継いだ回もあった。
**対策**: 下線が1件にしかなく、その断片にステータスバーが写っていれば、それはホバー。リスト項目・名前には下線を付けない（`hover:underline` にする）。ステータスバー自体も描かない。
土台のコードに `underline` があれば、書き始める前に grep で消す。

### 断片をまたぐリストは「同じタイトルが2回出る」を重複と決めつけない。前後の並び・数値・書影で件数を数える
**観察**: リストに同じタイトルの項目が2回ある（別の回の同名連載など）のを、断片の重なりと読んで1件にまとめ、先頭の1件を落とした。
judge は拾わず、書影の色が似ていてぼかし後の差も小さく layoutDiff も通った。この欠落で外枠が短くなり、別の列（sticky 列の押し上げ）のずれとして出た。
**対策**: 断片の重なりを判定するときは、タイトルではなく**直前・直後の項目の並び**と、項目ごとの数値（反応数など）・書影の色で数える。
同じタイトルでも前後の並びが合わなければ別の項目として全部入れる。組んだら各断片に写る項目の先頭タイトルを参照と1つずつ照合し、書影の色を probe color で1点測る。

### 期待 primitive は書き始める前に全部確認し、1ターン目で全部入れる
**観察**: ターゲットの Radix 期待リストに1つでも未使用が残ると、それだけでターンが増える。フォームの画面で `Form` を初回に入れず、次のターンで Form に寄せたら `Label` が消え、3ターンかかった。
**対策**: リストを読んで「どの要素をどの primitive で作るか」を先に対応づけてから書く。
`Form` があるなら Form.Root / Form.Field / Form.Label / Form.Control で組む。

### 知見は「例外」と一緒に渡す。部分的な規則は効きすぎる
**観察**: 規則の前半（「多数派に合わせて止める」「palt は付けない」）だけを渡した版では、エージェントが規則を広く当てはめ、本来直すべき所まで止めた。同じ古い版を渡した回は、毎回同じ所で止まった。
**対策**: 知見を書くとき・渡すときは、規則とその適用範囲・例外を1つの項目にまとめる。理由（なぜそうするか）を削らない。
