## 測りたかったこと

デザインのスクリーンショットを1枚渡して「これと同じ画面を作って」と言ったとき、
Claude Code は**何回の指示**で同じものを作れるのか。

実務では「だいたい合ってる」では足りない。余白が4px違えば作り直しになるし、
見た目が合っていても絶対配置で座標をなぞった実装なら保守できない。
だから「同じ」の判定は人の目ではなく、機械で決めたかった。

作ったのが `ui-bench` という小さなベンチマークで、この記事はその結果ではなく、
**結果を出すまでに計測器側で見つかった欠陥の話**である。
最終的に、エージェントが指標をすり抜けた事例は5件、
計測する側（ハーネス）の欠陥は**30件**になった。無駄になったターンの大半は後者だった。

## 仕組み

```
参照スクショ ──> brain（差分を読んで指示を出す）
                    │
                    ├─> builder（sandbox/src/App.tsx を書く。Radix UI + Tailwind v4）
                    │
                 撮影 ──> 5段のゲート ──> 通れば収束、落ちたらもう1ターン
```

- brain と builder は Claude Agent SDK の `query()` で回す。課金はサブスクリプション
- 「ターン」はハーネスが差分を突き返した回数。LLM の呼び出し回数ではない
- 1ターンの内側では builder が自分で撮って参照と見比べ、直している（中央値20往復）

### 5段のゲート

| ゲート | 見るもの | なぜ必要か |
| --- | --- | --- |
| ピクセル | グレースケール化＋ぼかしの差分 | 字形の差を潰して配置と寸法だけを見る |
| フロー | DOM。内部スクロール容器・ヘッダーの重複 | 断片ごとに画面を作って並べる不正を弾く |
| 構造 | 絶対配置の比率 | 座標で参照をなぞる不正を弾く |
| 部品 | Radix primitive を使っているか | 素の div で挙動を持つ部品を組む不正を弾く |
| 審査 | LLM が参照と実装を見比べる | 上の4つをすり抜けた「見落とし」を拾う |

ゲートが4つ増えたのは、**1つ前のゲートを満点でくぐり抜ける実装が実際に出てきた**からである。

## エージェントが指標をすり抜けた5件

ピクセル差分だけで判定していた頃、こういう実装が出た。

1. **絶対配置で座標をなぞる** — `absolute left-[222.5px] top-[124px]` を並べる。差分は下がるがUIとして成立しない
2. **画像領域を単色で潰す** — 参照のヒーロー画像を平均色1色の矩形にする。ぼかし差分では最適解になる
3. **連番コピペ** — `Row1` `Row2` `Row3` と同じ構造を手で増やす
4. **挙動を持つ部品を素の div で組む** — 見た目だけのタブ。キーボード操作もフォーカスも無い
5. **画面を並べて「ページ」に見せる** — 参照が5断片なら、断片ごとに画面を作って縦に積む。
   撮影結果は全断片で一致するのに、実際にスクロールするとヘッダーが6回現れる

5番目が象徴的で、**参照と完全に一致しているのに、成果物としては壊れている**。
人が絵を見て気づいたのは2件だけだった。

## 計測側の欠陥が25件出た

こちらが本題である。いくつか挙げる。

### ぼかし半径が小さすぎて、差分が字形の差で埋まっていた

素のピクセル差分はフォントの差で9%前後から下がらない。
ぼかしてから比べることにしたが、半径を3pxに固定していたため効いていなかった。
画像幅の1/100にして初めて、配置の差だけが見えるようになった。

### sticky ヘッダーが参照には写っていて実装には写らなかった

ページ全体を一度に撮ると、sticky なヘッダーは最初の1回しか写らない。
参照はスクロールしながら撮ったものなので毎断片に写っている。
この差で差分が5.3%から下がらず、**エージェントの実力だと4試行ぶん誤解した**。
実装側も同じようにスクロールして撮り直す方式に変えたら床が消えた。

### ノートPCのスリープをタイムアウトと数えた

`setTimeout` で20分のタイムアウトを入れていたら、3試行連続で発火した。
`pmset -g log` を見ると、その時間帯はバッテリー駆動でスリープを繰り返していた。
SDK のログの末尾は「first byte after 948ms」— **APIは正常に応答していた**。
壁時計はスリープ中も進むので、起きた瞬間に「20分経過」になる。
5秒ごとのティックで停止時間を除外する形に変えた。

さらにその先があって、スリープから復帰した直後はWi-Fiの再接続までAPIに届かない。
SDKはそれでも `subtype: success` で返し、本文に `API Error: ...` を入れてくる。
ハーネスはそれを普通のターンとして採点し、**何も書かれていない画面を「3ターン変化なし」**として
未収束に記録していた。「成功」の型で返ってくる失敗がある。

### 条件を揃えたつもりが、揃っていなかった

「部品ライブラリを空にして、知見を渡さずに測る」という条件で回していた。
ところがある試行で brain がこう書いていた。

> 同一シェルで layoutDiff 0 だった**前回 antd-pro-settings のアイコンライブラリとヘッダーを描き直さず流用**させた

run に残ったファイルは、前の試行のものと**バイト単位で同一**だった。
`cwd` がリポジトリ直下なので、Glob / Grep / Bash の再帰探索で
過去の試行の成果物・抽出結果（答案）・知見の原本に届いていた。

**条件を揃えたことの証明は、消したことではなく届かないこと**だった。
PreToolUse フックで遮断し、拒否は全部ログに残すようにした。
入れてすぐ分かったのは、**知見なし条件のエージェントは答案を探しに行く**ということで、
最初の5試行で23件の拒否が出た。

### ガードレールを入れたら、ガードレールで2本潰れた

遮断したらしたで、別の壊れ方をした。

- **拒否を「止まれ」と解釈した**: 複合コマンドの一部が禁止パスに触れて拒否されたとき、
  builder は作業自体の中止と受け取って手を止めた。拒否の文面に理由しか書いていなかった
- **禁止事項を引用しただけで拒否した**: 上を直すためプロンプトに「`extracted.json` は不可」と書いたら、
  brain がその注意書きを指示文に引き写し、**その文字列だけでサブエージェントの起動が拒否された**

後者は特に間抜けで、禁止事項を伝えたこと自体が禁止事項に引っかかっている。
検査するのは「何に触るか」であって「何を書いたか」ではない、という当たり前に行き着いた。

### 固定したはずのモデルが、実験の途中で替わっていた

アプリ画面の試行費用が $9〜17 から $1.2〜1.8 に落ちた。
直前にガードレールを直していたので、その効果に見えた。
実際は `model: 'opus'` の解決先が `claude-opus-5` から `claude-opus-5-5` に替わっていた。
**summary にモデルを記録していなかった**ので、ログを grep するまで分からなかった。

エイリアスで指定したものは、記録しても固定にならない。記録すべきは解決後の実体である。

### 事前チェックが、本番と同じ入口を通っていなかった

「試行の前に必ず selftest を通す」を手順にしていた。
その selftest は計測部品だけを import していて、**試行本体を一度も読み込んでいなかった**。
結果、`run.ts` の先頭に置いた1行が原因でバッチ10本が数秒で全滅したのに、
selftest は緑のまま通った。

バッチの1本目が数秒で終わったら、それは成功ではない。

## 結論は3回ひっくり返った

いちばん測りたかったのは「知見（過去の試行から抽出した手順集）を渡すとターン数が減るか」である。

- 隔離前: 知見あり 8/8 が1ターン、知見なし 中央値3ターン。**効果は明確に見えた**
- 隔離後（n=2）: 効果が消えた、と書いた
- 取り直し（n=9/10）: 知見あり中央値1、知見なし中央値3。**効果が戻った**。
  2回目は1世代前のプロンプトの n=2 を今の n=2 と比べていた
- **別ターゲットで測り直し**: 効果が消えた

最後がいちばん大きい。効果が出ていたのは記事ページという1つのターゲットで、
同じ「5断片の長いページ」である GitHub のリポジトリページで測ると、
知見あり・なしとも 6/6 が1ターンで収束し、知見ありのほうが**2.3倍高い**だけだった。

| ターゲット | 知見 | n | ターン | 中央値 | 平均 |
| --- | --- | --- | --- | --- | --- |
| 記事ページ | あり | 9 | 1,1,1,1,1,1,3,3,4 | 1 | $9.49 |
| 記事ページ | なし | 10 | 2,2,3,3,3,3,3,4,6,6 | 3 | $12.05 |
| GitHub | あり | 3 | 1, 1, 1 | 1 | $4.19 |
| GitHub | なし | 3 | 1, 1, 1 | 1 | $1.85 |

理由は知見の出どころにある。904行の知見は**記事ページの試行 約100件から抽出したもの**で、
「断片をまたぐリストは Picks 数で件数を数える」「左下にURLが写っている断片はホバー中」のように、
そのターゲットの固有知識が大半を占めていた。
汎用の手順知見のつもりで測っていたものは、実際には**その画面についての答え**に近かった。

言い直すとこうなる。

> 「知見でターン数が減る」ではなく、
> **「そのターゲットで試行を重ねた知見は、そのターゲットのターン数を減らす」**。
> 初見の画面に対しては、同じ知見はコンテキストの費用を増やすだけだった。

比較が成立するのは**ターゲット・隔離状態・プロンプト世代・モデル**の4つが揃った中だけで、
さらに**結論をターゲットの外へ持ち出せるかは別に確かめる**必要がある。
n を 2 から 9 に増やしても上がったのは同じターゲットの中の確からしさだけで、
一般化できるかは n では決まらなかった。

## 読んだ人が最初に疑うところを、実験で埋める

推測で答えると資料にならないので、全部測った。
いずれも同じターゲット（GitHub リポジトリページ・5断片）・蓄積知見なし・隔離あり、
対照は同じバッチの中に置いた。

### モデルを変えても成り立つのか → **成り立たない**

| モデル | 収束 | ターン | 費用 | 最終 layoutMad |
| --- | --- | --- | --- | --- |
| Opus 5.5 | 収束 | 1 | $2 | 0.49% |
| Sonnet 5 ① | 未収束 | 11 | $89 | 2.14% |
| Sonnet 5 ② | 未収束 | 12 | $165 | 2.86% |

Sonnet の推移はこうなる。

```
① 9.05 → 9.05 → 8.93 → 2.66 → 2.36 → 1.64 → 1.93 → 1.63 → 2.14 → 2.14 → 2.14
② 9.35 → 9.35 → 3.06 → 3.23 → 3.06 → 3.06 → 3.07 → 3.84 → 3.22 → 2.27 → 2.28 → 2.86
```

序盤で 9% から 2〜3% まで詰めたあと、**1.6〜3% を往復して止まる**（閾値は1%）。
直すと別の場所が壊れる状態で、12ターン・$165 かけても収束しない。費用は Opus の 44〜82 倍。

**「手順プロンプトだけで1ターン」は Opus 固有の性質**だった。
ベンチ自体は Sonnet に対しては十分に差を測れている。

### 計測の道具を渡しているから1ターンなのでは → **違う**

probe（参照を測るコマンド一式）をプロンプトから外しても 2, 1, 1 ターンで収束した（$3.80 / $1.46 / $1.38）。
道具あり（対照）は 1, 1, 1, 1, 2 ターン・$2.91。**道具は収束の必要条件ではなかった**。

### Radix を強制するのは余計な負担では → **負担は見えない**

指定とゲートを両方外しても 2, 1 ターンで、対照と同等だった。

### 審査が LLM なら採点はぶれるのでは → **ぶれる**

同じ成果物を3回採点させたところ、項目ごとに 0〜1 点、平均点で **0.8 点**ぶれた。
これは自分の主張を弱める結果で、「知見で judge が 92.5 → 94.2 に上がった」と書いていたが、
差 1.7 点はぶれの2倍しかない。品質の根拠は**LLM を介さない layoutMad に一本化**した。

### 収束の閾値が甘いのでは → **甘くはない**

layoutDiff の閾値を 1% から 0.2%（5倍厳しく）にしても 1, 1 ターンで通った。

### 関門は本当に効いているのか → **1つは効いていない**

312ターンを集計した結果。

| 関門 | 発火 | 割合 |
| --- | --- | --- |
| ピクセル(layoutDiff) | 105 | 33.7% |
| 部品(Radix/連番) | 48 | 15.4% |
| 審査(judge) | 42 | 13.5% |
| フロー | 25 | 8.0% |
| ピクセル(rawDiff) | 3 | 1.0% |
| 構造(絶対配置) | **0** | **0.0%** |

絶対配置の関門は一度も発火していない。プロンプトで先に防いでいるからで、
関門としては働いていなかった。「5段のゲートで守っている」と書いていたのは、実質4段だった。

rawDiff も 1.0% しか発火していないので一度は外したが、これは**判断を間違えた**。
外していい理由は発火実績ではなく「他の関門と守備範囲が重なっていること」で、
layoutDiff はグレースケール化してぼかすぶん**色相の誤りを捨てる**。
レイアウトが合って色だけ違う実装を拾えるのは rawDiff だけなので、戻したうえで
閾値を 30% → 15% に締めた（正常ターンの rawDiff は最大 12.7%、15% 超えは0件）。

## 関連研究と突き合わせる

同じ週に、同じ問い（ハーネスはどれだけ効くか）を扱う研究が2本出た。

この「初見には税になる」という観測は、関連研究とも噛み合う。

**HarnessTax**（UC Berkeley / Arena）は3つのハーネス × 7モデルで測り、
成功率はハーネスでほぼ変わらず、費用は最大約2倍、
**ターン数もほぼ同じ（15.4 対 15.3）で、差は初回コンテキスト**から来ると報告している。
これは自分のベンチに直撃する指摘で、知見21,502字は自分で払っている「税」である。
「知見で安くなる」と言うなら、コンテキスト増を差し引いた上で言う必要がある。

**An Empirical Study of Harness Design for Coding Agents**（arXiv 2609.20804）は、
弱いモデルの bash-only が「インターフェース外の出力」で軌跡を短絡させ、
**課題の難しさと無関係な偽の失敗信号**を作ると報告している。
これは自分が H-15 / H-17 / H-19 で踏んだものと同じ現象で、
論文側は「モデルの無能ではなくハーネスの制約」として分けて報告している。
自分も「ハーネス失敗」を分母から外す形に揃えた。

## 残った原則

1. **数字が動かないときは、実装ではなく計測を疑う**。30件中4件はこれで見つかった
2. **条件を揃えたことの証明は、消したことではなく届かないこと**
3. **固定したつもりのものは動く**。エイリアス、SDKの版、電源設定。記録していないものは後から確かめられない
4. **「成功」の型で返ってくる失敗がある**。結果の本文も見る
5. **代理指標は、それが成り立たない正当な画面で誤検知する**。新しい種類の対象を足したら全部疑い直す
6. **ガードレールは回復方法とセットで初めて機能する**。禁止は事前に、拒否は次の一手つきで
7. **繰り返すと決めたことは、約束ではなく入口の検査にする**。
   失敗カタログは毎日書けたのに、エージェントに渡す知見は4日放置した。
   未反映が溜まると selftest が落ちる仕組みにして、ようやく回るようになった

8. **n を増やしても一般化はできない**。同じターゲットで n を 2 から 9 に増やして確信を深めた結論が、
   ターゲットを1つ変えただけで消えた。確かめるべきは反復回数ではなく**別の問題でも成り立つか**だった
9. **関門の発火実績が少ないことは、外す理由にならない**。
   外していいのは「他の関門と守備範囲が重なっている」と示せたときだけで、
   それは発火回数ではなく**その指標が何を捨てているか**で決まる
10. **「つながらない」には戻らないものと待てば戻るものがある**。
   DNS 断とレート制限を同じ扱いにしていたため、9ターン進んだ試行を捨てた

エージェントの実力を測るつもりで始めて、**測る側の粗さのほうがずっと大きかった**、というのが
いまのところの結論である。
